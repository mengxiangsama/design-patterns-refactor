# 消息队列拓扑与应用侧实现

用于已有或计划采用的消息系统逻辑拓扑。先确认 MQ 产品/版本、业务流、消费者职责、峰值量、延迟、顺序、保留与重放要求；未确定产品时给逻辑方案及选型条件，不虚构可直接部署的参数。

## 拓扑决策

- 按业务事实与消费职责定义事件，区分命令和已发生的事实。说明生产者、Topic/Exchange、Queue/订阅、路由键、消费组和重试/死信去向；产品没有的概念不强行套用。
- 明确哪些消费者需要各收一份、哪些实例竞争同一份工作。Kafka 消费组与 RabbitMQ 队列绑定等机制按实际产品处理，不能把不同业务订阅放进竞争组导致漏掉各自应执行的动作。
- 确定排序范围：全局、实体或无需顺序。按业务键分区/路由，说明重试、并行处理和扩分区对顺序的影响；不保证跨分区顺序。
- 根据负载与处理耗时估算并发、分区/队列数、批量和积压恢复能力；缺少测量时给假设和验证方法，不给无依据的“最佳”数量。

## 契约与失败路径

- 定义事件 ID、业务键、实体版本、事件类型、Schema 版本和必要时间字段；区分投递重试与新的业务事件。保持字段演进兼容，说明旧消费者和历史消息如何处理。
- 指定确认/提交位点时机、重试责任和重放入口。避免应用层与客户端同时重试造成倍增；毒消息不得无限阻塞正常处理，死信保留原因和可追溯原消息。
- 重放沿用可去重的业务标识，明确幂等有效期与外部副作用。延迟重试可能破坏同一实体的顺序，应明确阻塞、版本校验或业务状态机的取舍。
- 定义过期、保留、死信修复和积压时背压策略，说明积压是否影响业务成功语义。消息保留不足可能导致无法恢复，应与一致性窗口和对账方案一起设计。
- 涉及跨数据库与消息写入、消费幂等及恢复时读 distributed-consistency.md；涉及协议演进时读 contract-and-event-migration.md。

交付一张可理解的拓扑图和端点配置表，覆盖正常、重试、死信与重放路径。可按请求编写应用侧生产/消费代码及声明配置；验证路由、广播/竞争、确认丢失、重复、乱序和消费者重启。明确逻辑设计、配置校验、本地联调与真实集群验证的区别，不包含 Kubernetes、网关或监控平台配置。
