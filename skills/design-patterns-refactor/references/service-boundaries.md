# 服务边界与渐进迁移

用于评估服务拆分、合并及职责迁移。先识别业务能力和数据所有权，不能按表、Controller、代码行数或设计模式机械拆服务。

## 判断依据

- 在可访问仓库中追踪一个具体业务流程：入口、同步调用、事件、读写表、事务和外部副作用。标出共享数据库、跨服务直写、循环调用及共同发布关系。
- 列出必须原子成立的不变量及其所有者，例如余额扣减和流水记录。拆分后跨网络才能维持的不变量是显著成本，不默认用分布式事务弥补不合理边界。
- 比较保留现状、模块化整理、服务拆分或合并。依据业务职责、变更频率、团队所有权、独立扩缩容和故障隔离需求；没有流量与延迟数据时不声称拆分提高性能。
- 对每个建议说明职责、权威数据、API/事件契约、同步依赖及失败传播。高频往返、共享写入和必须同时发布可作为重新划分边界的证据，而非自动合并结论。

## 迁移与验证

- 明确新旧数据所有者和切换时刻；需要回填时设计快照/增量衔接、校验和写入收口。双写必须说明部分成功、重试及冲突处理，不能假定两个写入原子成功。
- 使用兼容的契约扩展、逐个消费者迁移、切换写入和最后清理等阶段；按实际系统调整顺序。列出每阶段可独立发布的服务及可回退条件。
- 影子流量或新旧对比应隔离扣款、扣库存等副作用。数据格式或所有权已改变后，代码回滚未必能恢复，需给出数据修复或前向恢复路径。
- 验证混合版本调用、旧消费者、请求超时和部分不可用。涉及跨服务事务或异步一致性时再读 distributed-consistency.md；涉及事件契约变更时读 contract-and-event-migration.md。

交付可评审的职责/数据归属表、关键调用关系、选择理由及分阶段修改清单。只对已提供的服务作结论，明确外部接口的已知契约和未知条件。
