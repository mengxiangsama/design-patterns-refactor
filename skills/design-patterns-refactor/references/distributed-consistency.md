# 分布式事务与最终一致性

用于跨服务写入、可靠事件、重复处理、对账与补偿。先定义业务不变量、权威状态、允许的不一致窗口、成功响应含义和超时后状态；最终一致性只在恢复条件成立时收敛，不能承诺无条件成功。

## 选型

- 先检查能否将强原子约束保留在同一所有者的本地事务内，或通过状态机与查询确认减少跨服务原子提交需求。
- 本地事务加持久化待办/Outbox：适用于提交后可靠推进后续动作。业务写入和待发记录需原子提交，投递可重试；写库后直接发消息仍存在崩溃窗口。
- Saga：适用于可分步提交且有业务补偿的长流程。明确协调状态持久化、每步结果与补偿顺序；补偿是新的业务操作，可能失败，也不能天然撤销已发货等不可逆动作。
- TCC：仅在参与方提供可靠的资源预留、确认和取消能力时采用；说明预留过期、重复确认/取消、空回滚、悬挂及乱序竞争处理。
- XA/2PC 或中间件事务：仅在实际数据库、驱动及协调器支持且成本可接受时考虑。核实版本与恢复机制，不把数据库事务覆盖到任意 HTTP 外部调用。
- 比较必要候选及维护成本，沿用能满足需求的已有机制。需要技术版本或产品语义时查项目配置及对应官方文档，不凭模式名称生成配置。

## 恢复闭环

- 记录持久化状态机、业务幂等键和允许的状态迁移。超时表示结果未知时先查询/核实，避免当作明确失败重复扣款。
- 幂等键代表业务动作及其版本/范围。并发去重需唯一约束或条件更新等原子保证；涉及数据库副作用时，去重记录与业务变更应在同一事务中提交。外部副作用用供应方幂等能力或可确认的业务流水协调。
- 消息确认应对应已持久化的处理结果；提交成功但确认丢失必须可安全重放。不要宣称消息系统的 exactly-once 自动覆盖外部数据库和支付接口。
- 说明重试责任、退避、终止条件、毒消息处理和人工修复入口。设计对账的权威来源、比较键、时间水位及修复规则；迟到数据不可直接判为丢失。
- 并发或乱序更新使用实体版本、条件迁移等实际约束；避免迟到的取消覆盖已完成状态。为保留期、重复消息有效期和幂等记录清理明确关系。
- 对不可补偿动作和补偿失败定义可持续恢复的状态，防止无限重试和重复补偿。可观测结果与待处理记录属于验证依据，不扩展为监控平台部署。

## 验证与交付

围绕实际实现验证关键故障窗口：业务提交前后崩溃、投递后未记成功、消费提交后未确认、重复/乱序、并发重试、依赖超时、补偿失败及恢复重启。使用有意义的事务/集成测试检验持久化结果；仅 mock 调用不能证明数据库原子性或消息持久性。

交付事务边界、状态迁移、失败处理表、所选方案及舍弃理由，并分别列出已验证故障和未覆盖条件。需要 MQ 时再读 message-topology.md；既有同步调用改事件时同时读 contract-and-event-migration.md。
