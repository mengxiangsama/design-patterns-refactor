# 契约与事件的渐进迁移

只在本次改动涉及这些边界时使用；现有契约足够清楚就保留，不自动把异常改为 Result，或把直接调用改为事件。

## 错误表示

1. 列出调用方实际依赖的返回值、错误码、异常类型和发生时机，以及失败前已经执行的写入或外部调用。
2. 内部需要明确错误类别时，在现有边界转换为原有对外协议；逐个迁移调用方，确认覆盖后再移除临时兼容层。
3. 区分数据不存在、业务拒绝、依赖不可用和状态未知。例如支付查询超时不能映射为“未付款”，数据库断连不能映射为“查无记录”。
4. 验证失败后的持久化状态。异常改成普通错误返回，可能使框架不再回滚；提前或延后校验也可能改变副作用。
5. 对外输出稳定且必要的信息，内部保留原始原因用于诊断。协议和失败语义的改变单列为行为变更，以已有需求或用户授权为依据。

## 从直接调用迁移到事件

- 先说明业务事实、主状态写入和后续动作，以及当前谁等待谁、失败是否回滚。仅降低代码耦合时，可先保留同步执行。
- 一次迁移一个后续动作，主状态仍在原有事务内保存。先验证新处理器的输入与结果，再切换原调用；比较新旧路径时抑制重复的付款、扣库存、发短信等真实副作用。
- 改为提交后或异步执行时，明确“主操作成功、后续动作尚未成功”的状态及恢复方式。提交后失败不会撤销已提交数据，内存事件也不保证进程崩溃后能恢复。
- 只有确需可靠交付且在授权范围内，才选择已有重试机制、持久化待办、Outbox 等方案，不默认增加 MQ 或数据库表。按实际需求验证幂等键、重复通知、通知失败重试及顺序约束。
- 不能可靠恢复时，不宣称迁移已经等价完成；保留原路径或明确方案的适用边界。

例：原流程“保存状态后通知外部”改为提交后通知，外部能否立即读到状态、通知失败由谁重试，都必须有答案。调用顺序的 mock 只能验证顺序，不能证明提交可见性。
