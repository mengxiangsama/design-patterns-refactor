# 从业务需求推荐架构

用户只给业务目标时，由 Skill 查项目和资料、比较方案并推荐。明确的组件要求作为约束。仅请求设计或只给目标时保持只读。

## 1. 从当前项目取证

- 从用户指定或正在打开的业务项目开始。定位相关 API、写入口、读入口和事务，确认谁拥有权威数据、哪些业务状态和对外行为必须保持。既有代码以文件和行号为证据。
- 查构建依赖、应用配置、数据库迁移、消息定义、现有连接器、测试及可访问的发布资料。区分代码依赖、本地示例、指定环境的配置和已验证的部署；分别记录组件、版本和证据范围。
- 从需求和现有行为提取目标、时效、顺序、失败后的可见结果与恢复窗口。对结论有影响、又无法从项目查到的缺口才问少量具体问题，例如同步给谁、最多允许延迟多久。先按已知事实和清楚标注的假设给有条件的方案。缺少业务仓库时说明范围，以业务假设继续设计。

## 2. 查与需求相关的组件和公开方案

用户指定的资料优先。默认浏览 [middleware-component-lab 组件目录](https://github.com/mengxiangsama/middleware-component-lab/blob/main/docs/components/README.md)，再读取相关章节。例如 [CDC 与数据管道](https://github.com/mengxiangsama/middleware-component-lab/blob/main/docs/components/data-pipelines.md)、[消息组件](https://github.com/mengxiangsama/middleware-component-lab/blob/main/docs/components/messaging.md)、[搜索与缓存](https://github.com/mengxiangsama/middleware-component-lab/blob/main/docs/components/search-cache.md) 或 [任务调度](https://github.com/mengxiangsama/middleware-component-lab/blob/main/docs/components/scheduling.md)。只读与备选方案有关的资料。

组件目录用于补全候选和关键验证点。是否采用看项目证据和用户约束。涉及版本、连接器、事务、确认、顺序或兼容性时，核对目标版本的官方文档。读取资料与代码用于评估，按当前授权操作。目录离线时，继续用项目证据给方案，标明尚待核实的配置和保证。

需要比较已知做法或验证关键假设时，先查 [公开方案与工程资料索引](public-designs.md)，再按业务场景和失败问题搜索官方文档、原始论文或实施团队的一手案例。外部搜索使用通用场景与公开术语。对有影响的资料记录原始链接、适用前提、版本或环境、故障边界，以及能迁移到当前项目的部分。把外部经验和项目已验证事实分别写清。用户要求收集时，在交付中附可复用的来源与取舍摘要，按用户指定位置保存。

## 3. 比较后交付推荐

- 用同一口径比较至少两个相关选项。先看直读、同库事务、模块内处理等直接方案，再看复用现有机制或有必要时引入组件。对照业务时效、一致性、写入口覆盖、故障恢复、上线改造与维护成本。如果某一路线被硬约束排除，说明具体原因。
- 先给推荐方案、采用理由和改选条件，再用一条数据流或简图标出源、处理者、目标和确认点。说明职责、权威数据、事件或接口契约、写入生效时机和受影响模块。复杂方案按需补顺序键、版本或幂等键、重试和死信、重放、对账、迁移与回退。用正常路径和真正可能出错的窗口定义验收。
- 按需读 [服务边界](service-boundaries.md)、[事务与恢复](distributed-consistency.md)、[消息拓扑](message-topology.md)、[事件契约](contract-and-event-migration.md)。明确结论依据、关键假设和待验证条件。小需求可以只推荐项目内改动，给简洁的验收步骤。

## 示例：要一个商品更新同步

- 如果需求是修改后详情立刻可查，且详情与修改都在同一系统，优先考虑事务提交后读权威商品库。核对缓存和从库是否影响读到新值。
- 如果目标是搜索索引，商品有后台和批量导入等多个写入口，项目已有 MySQL、RocketMQ 与 Elasticsearch，且具备 binlog 读取权限与保留窗口，可比较 `MySQL → Canal → RocketMQ → 索引消费者 → Elasticsearch`。示例的验证重点是源位点与发送确认、消费者幂等和版本保护、下架不被旧消息覆盖、快照和增量衔接，以及索引故障后的追平。
- 如果所有写入口都能与待发记录用同一个本地事务提交，且下游依赖稳定的业务事件，比较 Outbox 加现有投递机制。核对批量或直接写库的入口是否也能产生待发记录，演练提交后中断、送达后确认丢失和重复投递。

基于具体项目在这些选项中给出一套推荐。搜索投影由商品、SKU、价格等多份数据组装时，另外核对变更覆盖范围和统一版本规则。

## 示例：我要订单超时的方案

- 若指待支付订单超时关闭，先查订单的截止时间、支付状态和允许的关闭延迟。订单量较小且能接受一个扫描周期的延迟时，可持久化截止时间，由已有调度器按截止时间分批扫未支付订单。
- 要求接近到期处理，且已有支持延时投递的 MQ 时，可评估延时消息正常触发，定时扫描补漏。订单状态和截止时间保存在数据库。结合已有可靠投递机制处理创建订单后发消息失败，核对实际 MQ 版本支持的延时范围。两条入口共用按状态、截止时间和版本做条件更新的关单逻辑，重复投递不重复关闭或回收资源。
- 支付和关单并发时按订单与支付渠道的状态执行合法迁移。到期后收口新的支付入口。若已有交易仍可能成功，先查单并按渠道协议确认已关闭或达到确定的未支付终态，再提交本地关单。结果未知时保留待核对状态并重试，已支付及迟到支付按业务规则处理。验收覆盖支付先成功、渠道结果未知、延时消息重复、停机跨过截止时间以及补偿任务与消息同时执行。
