# Design Patterns Refactor

将“代码问题 → 设计选择 → 最小改造 → 行为验证”连起来。允许结论为不使用任何模式。优先使用项目已有惯例与语言能力。

## 先确定请求和边界

- 用户只要求解释、评估或方案：只读分析；明确要求实现、优化代码或生成案例：执行相应修改。既有授权继续有效。
- 确认仓库、目标模块、语言、构建方式、现有修改以及实际调用入口。未指定模块时先定位高价值候选，不直接全仓改造。
- 区分业务缺陷、维护成本、性能瓶颈。仅凭 if/else、多层继承或类名不能判定需要模式。
- 示例、测试桩和内存实现按演示目的评价；生产约束作为接入条件，不将 Demo 未接数据库认定为现有缺陷。
- 分析目标项目，不能假设安装本 Skill 的项目包含任何 com.design 包或 Java/Spring 环境。

## 找证据，再选方案

追踪调用方、输入、返回、错误和外部副作用。列出必须保持的行为：接口、默认值、金额精度、执行顺序、事务/重试边界等。引用实际文件和行号。

每个候选说明：问题证据、具体变化点、最简单的直接改法；确有结构变化需求时再比较模式方案及采用或放弃理由。无用代码清理不要求设计模式或新增抽象。已有稳定的两个分支不一定需要策略；返回类型或错误语义变化应单独说明，不能混入结构重构。

模式选型时阅读 [模式选型参考](references/pattern-selection.md) 中相关类别。它覆盖 GoF 23 种模式及常见领域模式，候选不限于这些名称。只选当前证据支持的模式，说明引入的类、调用层级和维护成本。

## 无用代码与方法内冗余

检查或清理无用代码时，先读 [无用代码清理](references/dead-code-cleanup.md)。范围包含未使用符号，也包含仍在调用的方法内部的无效赋值、无用计算、不可达分支和冗余判断。一般重构中发现这些问题也可按该流程处理，但不扩大用户指定范围。

“检查、分析、找出”默认只报告；明确要求清理、删除或实施优化时才修改。以数据流、可达性和副作用为依据，不把搜索无引用、覆盖率为零或返回值未使用当作可删除证明。无法证明行为不变的候选保留并标为待确认。

## 跨微服务分析与改造

覆盖服务拆分/合并判断、分布式事务方案、数据库最终一致性，以及消息队列逻辑拓扑和应用侧实现。按请求选择下方专项参考，不因普通单服务重构加载它们。明确可访问仓库、参与服务、数据归属和业务不变量；区分代码证据、运行证据与待验证假设。缺少信息时先完成已有证据支持的方案，标明影响选型的未知条件。

- 服务边界、拆分或合并：读 [服务边界与渐进迁移](references/service-boundaries.md)。
- 跨服务事务、可靠事件、对账补偿：读 [分布式事务与最终一致性](references/distributed-consistency.md)。
- Topic/Queue、路由、消费组、顺序、重试与死信：读 [消息队列拓扑](references/message-topology.md)。

跨服务实施需包含新旧版本共存、分阶段发布与可行的回退或前向恢复方案。设计文档不等于一致性已解决；分别报告实现、故障验证和部署状态。本能力不覆盖 Kubernetes、网关和监控配置，也不推断未提供仓库的隐藏依赖。设计所需的新表、MQ 等可作为候选；实际引入或外部变更依照用户请求范围，不能把方案评估视为部署授权。

## 实施与兼容性

1. 为受影响的既有行为保留或补充有意义的回归用例，必要时用同一组输入比较重构前后；新行为单独测试。缺少测试或外部依赖妨碍验证时，按需阅读 [行为基线与依赖隔离](references/behavior-and-dependencies.md)，先保护可观察结果，再调整结构。
2. 修改最小连贯范围，沿用命名、依赖注入与构建约定。新教学案例可隔离在独立目录；真实重构避免长期维护两份业务实现。
3. 按选定模式处理实际边界。例如注册表检测重复键；装饰器说明叠加顺序；适配器保留单位和错误映射；事件说明提交时机、顺序和失败语义。
4. 若原代码对未知类型静默返回，显式抛错属于行为变更，应保留兼容或取得该变更的业务依据。不要以“最佳实践”名义擅改协议。涉及异常返回或事件化时阅读 [契约与事件迁移](references/contract-and-event-migration.md)，明确失败时机、提交与通知边界。
5. Java/Spring 任务按需阅读 [Java 与 Spring 注意事项](references/java-spring.md)。其他语言使用其原生抽象，勿自动引入 Spring。
6. 运行与变更相关的测试和构建。工具缺失时检查已有 wrapper、项目文档及可用运行环境；准确区分静态检查、编译、单元测试、集成测试。
7. 文档写明如何扩展、何时不该使用、如何验证，以及尚未覆盖的行为。不自动升级框架或新增数据库/MQ 等基础设施。

性能声明需要同负载下的测量；少写分支、增加接口或应用设计模式本身不证明更快。

## 资源路由

- [无用代码清理](references/dead-code-cleanup.md)：检查或删除未使用代码、方法内无效赋值和冗余逻辑时读。
- [模式选型参考](references/pattern-selection.md)：选型或比较模式时读相关类别。
- [Java 与 Spring 注意事项](references/java-spring.md)：只在 Java/Spring 重构时读。
- [行为基线与依赖隔离](references/behavior-and-dependencies.md)：缺少回归测试，或网络、时间、数据库等依赖使测试难以执行时读；优先复用已有替换入口。
- [契约与事件迁移](references/contract-and-event-migration.md)：改变错误表示、调用顺序或将直接调用迁移为事件时读；不默认引入异步或 MQ。
- [可运行案例](references/examples.md)：需要重构前后代码或讲解扩展点时读。代码位于 Skill 自带的 assets/java-examples，安装后仍可使用。
- [交付模板](assets/refactoring-report.md)：需要形成可评审方案时使用，删去不适用栏目。

## 交付

先说明实际解决的问题，再给出选型理由、修改位置、兼容性和测试结果。方案与代码实现区分清楚；未执行测试或未发布仓库就如实写明。不得把示例当生产框架，或把本地准备完成等同于 GitHub 已发布。
